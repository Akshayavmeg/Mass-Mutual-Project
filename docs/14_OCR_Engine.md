# OCR Engine

# 14. OCR Engine

## 1. Introduction

The **OCR (Optical Character Recognition) Engine** is responsible for converting the text present in a cheque image into machine-readable text.

In this project, the OCR engine receives the preprocessed cheque image from the **Image Preprocessing Module** and extracts important textual information such as:

* Cheque number
* Account number
* Routing/transit number
* Payee name
* Amount
* Date
* Other printed cheque information

The extracted text is then passed to the **Cheque Data Extraction Module**, where the raw OCR output is converted into structured fields.

```text
Cheque Image
      ↓
Image Preprocessing
      ↓
┌──────────────────────┐
│     OCR Engine       │
│     Tesseract OCR    │
└──────────┬───────────┘
           ↓
      Raw OCR Text
           ↓
Cheque Data Extraction
           ↓
Structured Cheque Data
```

---

# 2. Objectives

The OCR Engine has the following objectives:

1. Extract text from cheque images automatically.
2. Identify text from different cheque regions.
3. Extract the required cheque information with high accuracy.
4. Provide confidence information wherever available.
5. Handle common variations in cheque image quality.
6. Minimize manual data entry.
7. Detect OCR failures and low-confidence extraction.
8. Provide structured output to the data-extraction module.
9. Maintain the original OCR result for audit and debugging.
10. Contribute toward the project target of **at least 95% OCR extraction accuracy**.

The 95% figure is a **target to be measured using the project's sample/test dataset**, not a guaranteed OCR performance level.

---

# 3. Selected OCR Technology

## 3.1 Tesseract OCR

The MVP will use **Tesseract OCR** as the primary OCR engine.

Tesseract is suitable for this project because it:

* Is open source.
* Can be integrated with Python.
* Works with OpenCV.
* Supports multiple languages.
* Can return recognized text and confidence information.
* Is suitable for prototyping and experimentation.

Python can communicate with Tesseract through a wrapper such as **PyTesseract**.

Architecture:

```text
Python Backend
      ↓
PyTesseract
      ↓
Tesseract OCR Engine
      ↓
OCR Result
```

---

# 4. Why Tesseract Is Selected for the MVP

The project is initially intended as a prototype using synthetic/sample cheque data.

Therefore, Tesseract provides a practical starting point without requiring a paid cloud OCR service.

The architecture will remain modular so that cloud OCR services can be evaluated later if required.

Possible alternatives include:

* Google Cloud Vision
* Azure AI Vision
* AWS Textract

However, these are **alternative options**, not technologies that the MVP will claim to use unless actually implemented and evaluated.

# 7. OCR Configuration

Tesseract can be configured according to the type of cheque image.

Important configuration parameters include:

* OCR language
* Page segmentation mode
* OCR engine mode
* Character whitelist
* Image resolution
* Region of interest

For example, a restricted character set can be useful when processing fields that are expected to contain only digits.

However, different cheque fields have different formats, so a single OCR configuration should not necessarily be applied to the entire cheque.

---

# 8. Region-Based OCR

Instead of treating the entire cheque as one large text region, the system can divide the cheque into logical regions.

Example:

```text
┌──────────────────────────────────────────┐
│ Bank Name                                │
│                                          │
│ Date: __________                         │
│                                          │
│ Pay to: ______________________________   │
│                                          │
│ Amount: ______________________________   │
│                                          │
│ Account No: __________                   │
│                                          │
│ Signature: __________                    │
│                                          │
│ Cheque No / MICR Information             │
└──────────────────────────────────────────┘
```

Possible OCR regions:

```text
Region 1 → Date
Region 2 → Payee
Region 3 → Amount
Region 4 → Account information
Region 5 → Cheque number
Region 6 → Other printed text
```

Region-based OCR can reduce interference from unrelated text.

---

# 9. Raw OCR Output

The OCR engine should preserve the raw output before applying field-specific parsing.

Example:

```text
BANK OF DEMO
Date: 15/08/2026

Pay to: John Doe

Amount: 25,000.00

Account No: 1002345678

Cheque No: 000123
```

This raw text should be stored separately from the structured fields.

---

# 10. OCR Bounding Boxes

Tesseract can provide the approximate location of recognized text.

Example:

```text
┌──────────────────────────────────────────┐
│ BANK OF DEMO                             │
│                                          │
│ Date: 15/08/2026                         │
│                                          │
│ Pay to: John Doe                         │
│                                          │
│ Amount: 25,000.00                        │
│                                          │
└──────────────────────────────────────────┘
```

Each detected text element can have information such as:

```text
Text
X coordinate
Y coordinate
Width
Height
Confidence
```

This information is useful for determining **where** a particular piece of text appears on the cheque.

---

# 11. OCR Confidence

OCR systems may provide confidence scores indicating how strongly the engine believes a recognized text element is correct.

Example:

| Extracted Text | Confidence |
| -------------- | ---------: |
| 000123         |         98 |
| John Doe       |         96 |
| 15/08/2026     |         94 |
| 25,000.00      |         89 |

Confidence values can help identify fields that require additional validation.

For example:

```text
Confidence ≥ configured threshold
        ↓
Potentially reliable

Confidence < configured threshold
        ↓
Additional validation / review
```

The exact confidence threshold should be calibrated using the project's test dataset.

---

# 12. Field-Specific OCR

Different cheque fields require different recognition strategies.

### Cheque Number

Expected format:

```text
Numeric
```

Example:

```text
000123
```

---

### Account Number

Expected format:

```text
Numeric or bank-defined alphanumeric
```

Example:

```text
1002345678
```

---

### Routing/Transit Number

Expected format depends on the banking system and cheque format.

The system should not hard-code one country's format unless the project explicitly targets that banking standard.

---

### Payee

Expected format:

```text
Text
```

Example:

```text
John Doe
```

---

### Amount

The amount may appear as:

```text
Numeric amount:
25,000.00
```

and/or:

```text
Amount in words:
Twenty Five Thousand Only
```

The system can compare these representations later as an additional validation rule.

---

### Date

Example:

```text
15/08/2026
```

The date parser should support the format(s) defined for the project's cheque dataset.

---

# 13. OCR Post-Processing

Raw OCR output may contain recognition errors.

For example:

```text
OCR Output:
10023O5678
```

where:

```text
O
```

may actually represent:

```text
0
```

Therefore, post-processing rules can be applied based on the expected format of each field.

Example:

```text
Raw OCR
   ↓
Field Format Validation
   ↓
Character Normalization
   ↓
Structured Value
```

However, the system should **not blindly replace characters**, because that could introduce incorrect data.

Any correction should be validated against known formats or banking records.

---

# 14. Data Extraction Relationship

The OCR Engine and Data Extraction Module have different responsibilities.

### OCR Engine

Responsible for:

```text
Image → Text
```

### Data Extraction Module

Responsible for:

```text
Text → Structured Fields
```

Example:

```text
Raw OCR:
"Pay to: John Doe
Amount: 25,000.00
Date: 15/08/2026"

             ↓

Structured Data:

{
  "payee_name": "John Doe",
  "amount": 25000.00,
  "date": "2026-08-15"
}
```

This separation makes the architecture easier to test and maintain.

---

# 15. OCR Validation

After OCR, the system should perform basic validation of the extracted result.

Checks can include:

* Required text exists.
* Expected fields are present.
* Numeric fields contain valid characters.
* Date can be parsed.
* Amount can be parsed.
* Cheque number follows expected format.
* Account number follows expected format.
* OCR confidence is acceptable.

Example:

```text
OCR Result
    ↓
Are required fields detected?
    │
 ┌──┴─────┐
 ▼        ▼
YES       NO
 │        │
 ▼        ▼
Continue  Low-confidence/
           Manual Review
```

---

# 16. Handling OCR Failure

OCR failure can occur because of:

* Poor image quality
* Heavy blur
* Low resolution
* Handwritten information
* Unusual cheque layout
* Background patterns
* Occluded text
* Damaged cheque

The system should not automatically assume that an OCR result is correct.

Example:

```text
OCR Failure
     ↓
Retry with alternate preprocessing
     ↓
OCR again
     ↓
Still unsuccessful?
     ↓
Flag for Manual Review
```

This provides a controlled fallback.

---

# 17. OCR Retry Strategy

A limited retry mechanism can be implemented.

Example:

```text
Attempt 1
Standard preprocessing
       ↓
OCR
       ↓
Low confidence
       ↓
Attempt 2
Enhanced preprocessing
       ↓
OCR
       ↓
Compare results
```

The system should limit the number of retries to avoid unnecessary processing time.

This is important because the overall project target is:

> **Processing time < 30 seconds per cheque**

---

# 18. OCR Result Structure

The OCR result should be stored in a structured format.

Example:

```json
{
  "cheque_id": "CHK-2026-000001",
  "ocr_status": "COMPLETED",
  "raw_text": "BANK OF DEMO\nDate: 15/08/2026\nPay to: John Doe...",
  "average_confidence": 94.2,
  "fields_detected": 6
}
```

The raw OCR result should be retained for debugging and audit purposes according to the project's data-retention policy.

---

# 20. OCR Accuracy Measurement

The project has a target of:

> **OCR extraction accuracy ≥ 95%**

This should be measured using a labeled sample dataset.

For example, suppose we create:

```text
100 sample cheque images
```

For every image, we know the correct ground-truth values.

Example:

```text
Ground Truth:
Cheque Number = 000123

OCR:
Cheque Number = 000123

Result:
Correct
```

If:

```text
95 out of 100
```

required fields are correctly extracted according to the defined evaluation criteria, the measured extraction accuracy would be:

```text
95 / 100 × 100 = 95%
```

The exact evaluation methodology will be documented in:

```text
docs/32_OCR_Evaluation.md
```

# 22. OCR and Fraud Detection

OCR output also becomes an input to fraud detection.

For example:

```text
OCR Extracted Account
        ↓
Compare with Banking Record
        ↓
Match?
   ┌────┴────┐
   ▼         ▼
  YES        NO
   │         │
   ▼         ▼
Continue   Fraud Indicator
```

Similarly:

```text
OCR Amount
     ↓
Compare with amount in words
     ↓
Mismatch?
     ↓
Fraud/validation indicator
```

Therefore, OCR is an important upstream component of the fraud-detection pipeline.

# 24. Security and Privacy

Cheque images and OCR output may contain sensitive financial information.

Therefore:

* Real customer cheque data should not be used in the public GitHub repository.
* The project should use synthetic/sample cheque data for development and demonstration.
* Uploaded files should be stored securely.
* OCR output should have controlled access.
* Database credentials must not be hard-coded.
* Secrets should be stored using environment variables or a secure secret-management mechanism.
* Logs should not unnecessarily expose complete account numbers or other sensitive information.

# 26. Functional Requirements

The OCR Engine shall:

1. Receive preprocessed cheque images.
2. Process supported cheque images using Tesseract OCR.
3. Extract raw textual information.
4. Provide OCR confidence information where available.
5. Support field-specific OCR strategies.
6. Preserve raw OCR output.
7. Detect low-confidence results.
8. Support limited OCR retry processing.
9. Pass OCR results to the data extraction module.
10. Record OCR processing metadata.
11. Support OCR accuracy evaluation.
12. Handle OCR errors without crashing the complete application.

---

# 27. Non-Functional Requirements

### Accuracy

The project target is:

```text
OCR extraction accuracy ≥ 95%
```

### Performance

OCR should contribute to an overall processing time of:

```text
< 30 seconds per cheque
```

### Reliability

OCR failures should be handled gracefully.

### Maintainability

The OCR engine should be implemented as an independent service/module so that Tesseract can later be replaced by another OCR provider if required.

### Scalability

The architecture should allow OCR processing to be moved to a separate service or worker if cheque-processing volume increases.

# 30. Module Boundary

The OCR Engine is responsible for:

```text
✓ Receiving preprocessed image
✓ Running OCR
✓ Producing raw text
✓ Producing confidence information
✓ Providing text locations where available
✓ Detecting OCR failure
✓ Limited retry processing
✓ Recording OCR metadata
```

It is **not responsible for**:

```text
✗ Banking-record validation
✗ Account verification
✗ Payee verification
✗ Duplicate detection
✗ Fraud scoring
✗ Final approval/rejection
```

Those functions belong to subsequent modules.

# 33. Final Design

The OCR Engine is therefore designed as a **separate, replaceable service/module** within the cheque-processing pipeline.

```text
┌──────────────────────────────────────────────────┐
│              CHEQUE PROCESSING SYSTEM            │
├──────────────────────────────────────────────────┤
│                                                  │
│ Input                                             │
│   ↓                                              │
│ Preprocessing                                    │
│   ↓                                              │
│ ┌──────────────────────────────────────────────┐ │
│ │                 OCR ENGINE                  │ │
│ │                                              │ │
│ │  Preprocessed Image                         │ │
│ │          ↓                                   │ │
│ │      Tesseract                              │ │
│ │          ↓                                   │ │
│ │      Raw Text                               │ │
│ │          ↓                                   │ │
│ │ Confidence + Bounding Boxes                 │ │
│ └──────────────────────┬───────────────────────┘ │
│                        ↓                         │
│              Data Extraction                    │
│                        ↓                         │
│                 Validation                      │
│                        ↓                         │
│              Fraud Detection                   │
│                        ↓                         │
│                 Risk Scoring                    │
│                        ↓                         │
│              Approve / Review / Reject          │
│                                                  │
└──────────────────────────────────────────────────┘
```

**Key implementation decision:** for our `Mass-Mutual-Project` MVP, we will use **Python + Tesseract/PyTesseract + OpenCV**, evaluate OCR against our own synthetic cheque dataset, and only claim the **≥95% OCR target** if our measured test results actually achieve it.
