# Scope and Assumptions

# 05. Scope and Assumptions

## 1. Introduction

This document defines the **scope, boundaries, assumptions, dependencies, and constraints** of the AI-Powered Cheque Scanning, Validation & Fraud Detection System.

The purpose of this document is to clearly identify what the project will implement, what it will not implement, and the conditions under which the proposed system will operate.

---

# 2. Project Scope

The system covers the complete **cheque image processing and decision-support workflow**, beginning with cheque image submission and ending with an **Approve, Manual Review, or Reject** recommendation.

The major in-scope capabilities are:

1. Cheque image upload/capture
2. Image validation
3. Image preprocessing
4. OCR-based cheque information extraction
5. Structured cheque data generation
6. Banking-record validation
7. Duplicate detection
8. Signature analysis where reference data is available
9. Image tampering detection
10. Anomaly detection
11. Fraud risk scoring
12. Decision workflow
13. Manual review workflow
14. Dashboard and reporting
15. Audit trail
16. Role-based access control
17. System evaluation and performance measurement

---

# 3. In-Scope Components

## 3.1 Cheque Image Upload and Capture

The system shall accept cheque images through:

* File upload
* Scanner
* Camera, where supported by the implementation

Supported file formats:

* JPEG/JPG
* PNG
* PDF

The system shall validate the uploaded file before further processing.

---

## 3.2 Image Validation

The system shall check whether the submitted image is suitable for processing.

Checks may include:

* File format
* File size
* Image dimensions
* Image readability
* Corruption
* Blur
* Orientation
* Basic image quality

Invalid files shall be rejected before OCR processing.

---

## 3.3 Image Preprocessing

The project includes preprocessing of cheque images using computer vision techniques.

Possible operations include:

* Grayscale conversion
* Noise removal
* Contrast enhancement
* Thresholding
* Resizing
* Deskewing
* Rotation correction
* Background normalization
* Region-of-interest detection

The preprocessing pipeline will be configurable based on the quality of the input cheque images.

---

## 3.4 OCR and Data Extraction

The system shall extract relevant cheque information using an OCR engine.

The target fields include:

* Cheque number
* Account number
* Routing/transit/bank identifier, where applicable
* Payee name
* Amount
* Date
* Currency
* MICR-related information, where available
* Signature region

The system shall preserve OCR confidence information where supported.

---

## 3.5 Banking Data Validation

The extracted cheque information shall be validated against **mock banking records or an approved banking data source**.

The validation scope includes:

* Account existence
* Account status
* Cheque number/series
* Date validity
* Payee matching
* Amount validation
* Duplicate transactions
* Cross-field consistency

For the project prototype, mock banking data will be sufficient.

---

## 3.6 Fraud Detection

The system shall analyze cheque information and image characteristics for potential fraud.

The fraud-detection scope includes:

### Image Tampering

Detection of suspicious modifications in cheque regions such as:

* Amount
* Payee
* Date
* Cheque number
* Signature

### Duplicate Detection

Identification of previously processed or highly similar cheques.

### Signature Analysis

Comparison against a reference signature where appropriate reference data is available.

### Anomaly Detection

Identification of unusual transaction behavior using available historical/mock data.

### Rule-Based Fraud Checks

The system shall support configurable fraud and validation rules.

---

## 3.7 Risk Scoring

The system shall calculate a risk score based on relevant signals generated by:

* OCR confidence
* Validation failures
* Duplicate detection
* Signature analysis
* Image tampering analysis
* Anomaly detection
* Other configured fraud indicators

The risk score shall be used by the decision engine to determine the appropriate workflow.

---

## 3.8 Decision Workflow

The system shall provide three primary decision outcomes:

```text
APPROVE
   │
   ├── Low-risk / valid cheque
   │
MANUAL REVIEW
   │
   ├── Uncertain / suspicious case
   │
REJECT
   │
   └── Critical validation or high-risk case
```

The decision thresholds shall be configurable.

---

## 3.9 Manual Review

Cases requiring human verification shall be placed in a manual-review queue.

Reviewers shall be able to access:

* Original cheque image
* Extracted information
* OCR confidence
* Validation results
* Fraud indicators
* Risk score
* Supporting evidence
* Processing history

The reviewer shall be able to record the final decision and comments.

---

## 3.10 Dashboard and Reporting

The project includes a dashboard for monitoring system activity.

The dashboard shall provide information such as:

* Total cheques processed
* Approved cheques
* Review cases
* Rejected cheques
* Fraud alerts
* Risk distribution
* Processing time
* OCR performance
* Validation failures
* Review workload

Reports shall support analysis of processing and fraud-detection performance.

---

## 3.11 Audit Trail

The system shall maintain an audit trail for every processed cheque.

The audit trail shall record important events including:

* Upload
* Preprocessing
* OCR
* Extraction
* Validation
* Fraud analysis
* Risk scoring
* Decision
* Manual review
* Final disposition

The audit information shall allow an authorized user to understand how a particular decision was reached.

---

## 3.12 Security and Access Control

The project includes basic security controls appropriate for the prototype.

These include:

* User authentication
* Role-based access control
* Restricted access to cheque information
* Secure handling of credentials
* Protection of sensitive information
* Audit logging of important user actions

---

# 4. Out of Scope

The following capabilities are explicitly **outside the scope of this project**.

## 4.1 Real-Time Payment Settlement

The system will **not** perform actual payment settlement or transfer money between bank accounts.

It will only provide cheque-processing and decision-support functionality.

---

## 4.2 Core Banking System Replacement

The project will not replace or replicate a bank's:

* Core banking platform
* Account management system
* Payment processing system
* General ledger
* Clearing infrastructure

The prototype will interact with mock/approved data through defined interfaces.

---

## 4.3 Real-Time Banking Network Integration

The prototype will not directly connect to live banking networks, clearing houses, or payment networks unless explicitly authorized and technically provided.

---

## 4.4 Customer-Facing Mobile Application

A dedicated customer mobile application is outside the project scope.

The project focuses on the backend processing pipeline and an internal web-based dashboard/review interface.

---

## 4.5 Automatic Money Transfer

The system will not automatically debit or credit customer accounts.

The **Approve** result represents a processing recommendation/workflow state, not actual financial settlement.

---

## 4.6 Fully Autonomous Fraud Investigation

The system will identify suspicious cases and provide evidence, but it will not completely replace human investigators.

High-risk or uncertain cases may require manual investigation.

---

## 4.7 Production Banking Deployment

A production deployment into an actual banking environment is outside the initial prototype scope.

Production deployment would require additional:

* Regulatory approvals
* Security assessments
* Compliance reviews
* Banking integrations
* Infrastructure controls
* Operational procedures

---

# 5. Assumptions

The system will be developed under the following assumptions.

## A-001 — Sample Cheque Images

A suitable collection of sample cheque images will be available for development and testing.

The dataset should contain a reasonable variety of:

* Cheque layouts
* Image qualities
* Amounts
* Dates
* Payees
* Handwritten/printed information where applicable

---

## A-002 — Mock Banking Data

Mock or synthetic banking data is acceptable for the prototype.

The mock database may contain:

* Account records
* Account status
* Customer/reference identifiers
* Cheque numbers
* Cheque series
* Payee information
* Transaction history
* Reference signatures where legally and technically appropriate for testing

No real customer banking information is required for the prototype.

---

## A-003 — OCR Availability

An OCR engine such as Tesseract, Google Vision, or Azure AI Vision will be available during development.

If a cloud OCR service is used, the required credentials and API access will be configured securely.

---

## A-004 — Image Quality

The system assumes that submitted cheque images are reasonably readable.

Extremely blurred, severely cropped, heavily obstructed, or otherwise unreadable images may not produce reliable OCR results.

Such cases should be routed to manual review or rejected as **unprocessable**, depending on the configured workflow.

---

## A-005 — Reference Signature Availability

Signature comparison assumes that an authorized reference signature is available.

If a reference signature is unavailable, the system will not automatically classify the cheque as fraudulent solely because signature verification cannot be performed.

---

## A-006 — Historical Data

Anomaly detection assumes that sufficient historical or mock transaction data is available.

If historical data is insufficient, the system will rely on deterministic rules and available fraud indicators instead of producing unsupported behavioral conclusions.

---

## A-007 — Validation Rules

Banking validation rules will be represented using configurable business rules appropriate to the prototype.

Actual banking policies may vary between institutions and must be configured separately for a production implementation.

---

## A-008 — Processing Environment

The prototype will operate in a controlled development/test environment with sufficient:

* CPU
* Memory
* Storage
* Database capacity
* Network connectivity where cloud services are used

---

## A-009 — Human Review

The system assumes that authorized personnel will be available to review cases that cannot be confidently approved or rejected automatically.

The system is designed as a **decision-support and workflow automation system**, not an unrestricted autonomous banking decision maker.

---

## A-010 — PII and Financial Data

Any real financial or personally identifiable information, if introduced during future testing, will be handled according to applicable organizational security and privacy requirements.

Development should preferably use **synthetic or anonymized data**.

---

# 6. Constraints

The project has the following constraints:

### Technical Constraints

* OCR accuracy depends on image quality and cheque layout.
* Different cheque formats may require different extraction strategies.
* Signature analysis requires suitable reference data.
* Fraud detection performance depends on the quality and size of the training/evaluation dataset.
* Cloud OCR services may introduce API limits or additional costs.

### Data Constraints

* Real banking data may not be available.
* Mock data may not represent every real-world banking scenario.
* Fraud datasets can be highly imbalanced.
* Genuine fraudulent cheque samples may be difficult to obtain.

### Operational Constraints

* Manual review remains necessary for uncertain cases.
* The prototype does not perform actual cheque settlement.
* Production banking integration requires additional security and compliance validation.

# 9. Success Criteria

The project will be considered successful when the prototype demonstrates the complete cheque-processing workflow:

```text
Upload
  ↓
Preprocess
  ↓
Extract
  ↓
Validate
  ↓
Detect Fraud
  ↓
Calculate Risk
  ↓
Approve / Review / Reject
  ↓
Record Audit Trail
  ↓
Display Results
```

The project will additionally target:

* **≥ 95% OCR extraction accuracy**
* **≥ 90% fraud detection accuracy**
* **< 30 seconds processing time per cheque**
* **≥ 50% reduction in manual review cases**
* **60–80% reduction in manual verification effort**

These values are **target evaluation criteria**, not claims of achieved performance until validated using the project's test dataset.

---

# 10. Scope Summary

> **The project scope covers the design and development of an AI-assisted cheque processing system that accepts cheque images, performs image preprocessing and OCR extraction, validates cheque information against mock or approved banking records, detects potential fraud and anomalies, calculates a risk score, and routes the cheque to an Approve, Manual Review, or Reject workflow. The system also includes dashboard reporting, role-based access, and a complete audit trail. Real-time payment settlement, core banking replacement, live banking-network integration, and customer-facing mobile applications are explicitly excluded from the initial project scope.**
