# Cheque Input Module
# 12. Cheque Input Module

## 1. Introduction

The **Cheque Input Module** is the entry point of the AI-Powered Cheque Scanning, Validation & Fraud Detection System. Its primary responsibility is to receive a cheque image from the user, verify that the uploaded file is suitable for processing, register the cheque in the system, and pass the valid input to the **Image Preprocessing Module**.

The module supports both **manually uploaded cheque files** and, in future versions, cheque images captured using a camera or scanner.

The input flow is:

```text
User
  ↓
Upload / Capture Cheque
  ↓
File Validation
  ↓
Image Quality Validation
  ↓
Generate Processing ID
  ↓
Store Original Image
  ↓
Send to Image Preprocessing
```

---

# 2. Objectives

The Cheque Input Module has the following objectives:

1. Accept cheque images in supported formats.
2. Validate the uploaded file before processing.
3. Prevent unsupported or corrupted files from entering the pipeline.
4. Generate a unique identifier for every cheque.
5. Preserve the original cheque image for audit and verification.
6. Record basic metadata about the uploaded cheque.
7. Provide clear feedback to the user.
8. Pass valid cheque images to the preprocessing pipeline.
9. Prevent accidental duplicate submissions where possible.
10. Ensure that uploaded data is handled securely.

---

# 3. Supported Input Methods

The system is designed to support the following input methods.

### 3.1 File Upload

The primary MVP input method will be file upload.

Supported formats:

```text
JPEG (.jpg)
JPG (.jpeg)
PNG (.png)
PDF (.pdf)
```

Example:

```text
User
 ↓
Select Cheque Image
 ↓
Upload
 ↓
System Validation
```

---

### 3.2 Camera Capture

A camera-based capture interface can be added to allow a user to photograph a cheque.

```text
Camera
   ↓
Capture Image
   ↓
Image Validation
   ↓
Processing
```

Camera capture is considered an extension of the input module and is not required for the initial MVP if the project uses uploaded sample cheque images.

---

### 3.3 Scanner Input

The system may later support scanned cheque images generated by banking/scanning equipment.

The scanner output should ultimately be converted into one of the supported formats before entering the processing pipeline.

# 5. File Validation

Before a cheque enters the processing pipeline, the system performs file validation.

The following checks should be performed:

### 5.1 File Extension Check

The system verifies that the uploaded file has an allowed extension.

```text
Allowed:
.jpg
.jpeg
.png
.pdf
```

Example:

```text
cheque.jpg
      ↓
Allowed
```

But:

```text
cheque.exe
      ↓
Rejected
```

The system should not rely only on the filename extension; the actual file type/content should also be validated.

---

# 6. File Size Validation

Very large files should not be accepted unnecessarily because they increase processing time and resource usage.

Example prototype rule:

```text
Maximum file size = 10 MB
```

This value is configurable and can be changed through the project configuration.

Example:

```text
2.5 MB → ACCEPT
8 MB   → ACCEPT
15 MB  → REJECT
```

The final limit should be defined according to the deployment environment.

---

# 7. Image Dimension Validation

For image-based cheques, the system should check whether the image resolution is sufficient for OCR.

Example:

```text
Very Low Resolution
       ↓
OCR Reliability Concern
       ↓
Reject / Request Better Image
```

A high-quality cheque image should contain sufficient detail to identify:

* Cheque number
* Account information
* Payee
* Amount
* Date
* Other relevant fields

The exact minimum resolution should be established during OCR evaluation rather than arbitrarily treating one resolution as universally valid.

---

# 8. PDF Validation

If the user uploads a PDF, the system determines whether it contains a valid cheque image.

```text
PDF
 ↓
PDF Validation
 ↓
Extract / Render Page
 ↓
Cheque Image
 ↓
Preprocessing
```

For the MVP, the system should clearly define whether multi-page PDFs are accepted.

Recommended MVP rule:

> A PDF should contain one cheque image per processing request unless multi-page cheque documents are explicitly supported.

---

# 9. Image Quality Validation

Before OCR, basic quality checks should be performed.

Possible checks include:

* Blur
* Brightness
* Contrast
* Image dimensions
* Rotation/skew
* Excessive noise
* Missing image content
* Extreme cropping

Example:

```text
             Uploaded Image
                    │
                    ▼
            Quality Analysis
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Suitable           Unsuitable
          │                   │
          ▼                   ▼
      Continue          Request Re-upload
```

The detailed preprocessing operations are documented separately in:

```text
docs/13_Image_Preprocessing.md
```

# 10. Cheque Registration

After successful input validation, the system creates a unique processing record.

Example:

```text
Processing ID:
CHK-2026-000001
```

The processing ID is used throughout the entire system.

```text
CHK-2026-000001
        │
        ├── Original Image
        ├── OCR Result
        ├── Extracted Data
        ├── Validation Result
        ├── Fraud Result
        ├── Risk Score
        ├── Decision
        └── Audit Trail
```

This provides traceability across the entire processing lifecycle.

---

# 11. Input Metadata

When a cheque is uploaded, the system should store metadata such as:

| Field               | Description                              |
| ------------------- | ---------------------------------------- |
| `cheque_id`         | Unique processing identifier             |
| `file_name`         | Original uploaded filename               |
| `file_type`         | JPEG/PNG/PDF                             |
| `file_size`         | Size of uploaded file                    |
| `upload_timestamp`  | Time of upload                           |
| `uploaded_by`       | User/system identifier                   |
| `input_source`      | Upload/Camera/Scanner                    |
| `processing_status` | Current processing state                 |
| `file_hash`         | Hash used for integrity/duplicate checks |

Example:

```json
{
  "cheque_id": "CHK-2026-000001",
  "file_name": "sample_valid_001.jpg",
  "file_type": "image/jpeg",
  "file_size": 245678,
  "input_source": "UPLOAD",
  "processing_status": "UPLOADED"
}
```

---

# 12. File Hashing

A cryptographic hash can be generated for the uploaded file.

Example:

```text
Cheque Image
     ↓
SHA-256 Hash
     ↓
File Fingerprint
```

Example:

```text
File Hash:
8f4c...a91d
```

The hash can help identify whether the exact same file has already been submitted.

However, **file hashing alone should not be treated as complete cheque duplicate detection**, because the same cheque could be uploaded as a different image file.

The actual duplicate detection logic will be handled by the Duplicate Detection Module.

```text

   ↓

   ↓
```

# 18. Error Handling

The module should provide meaningful error messages.

| Error              | Example Response                                   |
| ------------------ | -------------------------------------------------- |
| Unsupported file   | "Unsupported file format."                         |
| File too large     | "File exceeds the maximum allowed size."           |
| Corrupted file     | "Unable to read the uploaded file."                |
| Poor image quality | "Image quality is insufficient for processing."    |
| Empty upload       | "Please select a cheque file."                     |
| Invalid PDF        | "Unable to extract a valid cheque image from PDF." |
| Processing failure | "Cheque could not be processed. Please retry."     |

The system should avoid exposing internal technical details to the end user.

---

# 19. Security Considerations

Because cheque images can contain sensitive financial information, the input module must follow secure handling practices.

Important controls include:

* Validate file type and content.
* Restrict maximum file size.
* Generate unique processing IDs.
* Avoid executing uploaded files.
* Store uploaded files securely.
* Restrict access to cheque images.
* Do not expose uploaded files through public URLs.
* Maintain audit records.
* Avoid committing real cheque images to GitHub.
* Use synthetic data in the public repository.
* Protect sensitive configuration and credentials using environment variables.

**Real customer cheque images or real banking records must not be placed in the Git repository.**

# 23. Input-to-Processing Contract

The Cheque Input Module must provide the next module with a valid processing object.

Example:

```json

  "cheque_id": "CHK-2026-000001",
  "file_path": "secure-storage/CHK-2026-000001.jpg",

  "status": "READY_FOR_PREPROCESSING"
```

The Image Preprocessing Module then receives this object and begins image enhancement.

# 24. Functional Requirements

The module shall:

1. Accept JPEG, JPG, PNG and PDF files.
2. Validate uploaded file type.
3. Validate file size.
4. Validate file integrity.
5. Perform basic image quality checks.
6. Generate a unique cheque processing ID.
7. Record upload metadata.
8. Store the original image securely.
9. Provide upload status to the user.
10. Reject invalid uploads with a clear reason.
11. Pass valid input to the preprocessing module.
12. Maintain traceability through the generated cheque ID.

---

# 25. Non-Functional Requirements

The module should provide:

### Performance

The upload and initial validation process should be lightweight enough not to become a bottleneck in the overall target of **less than 30 seconds per cheque**.

### Reliability

Invalid or corrupted files should not crash the processing pipeline.

### Security

Uploaded cheque information must be protected from unauthorized access.

### Scalability

The module should be capable of handling multiple cheque submissions as the system evolves.

### Maintainability

File validation rules and size limits should be configurable rather than hard-coded throughout the application.

# 27. Module Boundary

The Cheque Input Module is responsible for:

```text
✓ Receiving cheque
✓ File validation
✓ Basic image quality validation
✓ Metadata creation
✓ Unique ID generation
✓ Secure storage/reference
✓ Passing valid input forward
```

It is **not** responsible for:

```text
✗ OCR
✗ Detailed cheque field extraction
✗ Banking validation
✗ Fraud scoring
✗ Signature matching
✗ Final approval/rejection
```

Those responsibilities belong to the subsequent modules.
