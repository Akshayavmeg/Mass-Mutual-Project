# Database Architecture

# 24. Database Architecture

## 1. Introduction

The **Database Architecture** defines how data generated by the AI-Powered Cheque Scanning, Validation & Fraud Detection System is stored, organized, accessed, and protected.

The database acts as the central persistence layer for the project. It stores cheque information, OCR results, validation results, fraud detection results, risk scores, decisions, manual review cases, users, and audit records.

For the MVP, the system will use **PostgreSQL** as the primary relational database. **Synthetic/mock banking data** will be used instead of real banking data so that the complete workflow can be developed and demonstrated safely.

---

# 2. Database Objectives

The database architecture is designed to:

1. Store all cheque-processing information in a structured format.
2. Maintain relationships between cheques, accounts, customers, and processing results.
3. Store OCR-extracted cheque information.
4. Store validation results.
5. Store fraud detection results.
6. Store signature analysis results.
7. Store duplicate and anomaly detection results.
8. Store risk scores and risk levels.
9. Store automated decisions.
10. Store manual review cases and reviewer decisions.
11. Maintain a complete audit trail.
12. Support dashboard and reporting requirements.
13. Provide secure and controlled access to sensitive financial information.
14. Support future migration from mock banking data to authorized banking-system integrations.

---

# 3. Selected Database

## PostgreSQL

The project will use **PostgreSQL** as the primary database.

### Reasons for selecting PostgreSQL

* Open-source relational database.
* Strong support for structured financial data.
* ACID transaction support.
* Foreign-key and constraint support.
* Suitable for relational banking records.
* Supports indexing and efficient querying.
* Works well with Python backend frameworks.
* Suitable for development and production environments.
* Supports JSON/JSONB fields when semi-structured model results need to be stored.
* Can handle audit and transaction-oriented workloads.

```text

          │            │            │

                       │
```

# 25. Database Constraints

The database should use constraints to maintain data integrity.

Examples:

### Primary Keys

Every major table should have a unique primary key.

### Foreign Keys

Example:

```text
cheques.account_id
        ↓
bank_accounts.account_id
```

### NOT NULL

Critical fields such as:

```text
cheque_id
cheque_number
created_at
```

should not be empty.

### CHECK Constraints

Example:

```text
decision IN ('APPROVE', 'REVIEW', 'REJECT')
```

and:

```text
risk_score BETWEEN 0 AND 100
```

### Unique Constraints

Cheque identifiers that must be unique within the mock banking system should have appropriate unique constraints.

# 27. Transaction Management

Database transactions should be used for operations that require multiple related changes.

For example, when a reviewer approves a case:

```text
BEGIN TRANSACTION

Update manual_review_cases
        ↓
Store reviewer decision
        ↓
Update cheque status
        ↓
Create audit event

COMMIT
```

If any required operation fails:

```text
ROLLBACK
```

This prevents partially completed workflows.

# 30. Database Security

The database should implement:

* Authentication.
* Role-based access.
* Password hashing.
* Least-privilege database accounts.
* Encrypted connections where deployed.
* Sensitive-data masking.
* Input validation.
* Audit logging.
* Backup and recovery procedures.
* No hard-coded database credentials in source code.

Database credentials should be stored through environment variables or a secure secrets-management mechanism.

Example:

```text
DATABASE_URL=<secure configuration>
```

The actual credential must never be committed to GitHub.

```text
                              │
```

```text
                           Decision
                              │
                         ┌────┴────┐

                       Review    Audit

```

The architecture provides a **single, structured source of truth for the cheque-processing workflow**, while keeping banking data, analytical results, decisions, manual review information, and audit records logically separated.

For this project, **PostgreSQL + synthetic banking data + file/object references for cheque images** provides a practical architecture that is realistic enough for the hackathon prototype while remaining safe, reproducible, and extensible toward a production-grade system.
