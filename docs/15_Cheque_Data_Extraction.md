# Cheque Data Extraction

# 15. Cheque Data Extraction

## 1. Introduction

The **Cheque Data Extraction Module** converts the raw text and positional information produced by the OCR Engine into structured cheque data.

The OCR Engine answers:

> **“What text is present in the cheque image?”**

The Data Extraction Module answers:

> **“Which extracted text represents the cheque number, account number, payee, amount, date, routing/transit number, etc.?”**

This module is therefore responsible for transforming **unstructured OCR output into structured cheque fields** that can be consumed by the Validation Engine and Fraud Detection modules.

```text
┌──────────────────────────┐
│ 13. Image Preprocessing  │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│ 14. OCR Engine           │
│                          │
│ Raw text + coordinates   │
│ + confidence             │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│ 15. Data Extraction      │
│                          │
│ Field identification     │
│ Normalization            │
│ Format validation        │
│ Confidence assignment    │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│ Structured Cheque Data   │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│ 16. Validation Engine    │
└──────────────────────────┘
```

---

# 2. Objectives

The objectives of the Cheque Data Extraction Module are:

1. Convert raw OCR output into structured cheque information.
2. Identify individual cheque fields.
3. Normalize extracted values into consistent formats.
4. Validate extracted fields according to their expected data types.
5. Associate OCR confidence with each extracted field.
6. Detect missing or ambiguous fields.
7. Preserve the original OCR output for traceability.
8. Provide structured data to the Validation Engine.
9. Reduce incorrect interpretation of OCR results.
10. Support downstream fraud detection and duplicate detection.

---

# 3. Extracted Cheque Fields

The system should attempt to extract the following fields where they are present and applicable to the cheque format:

| Field                  | Description                                          | Example                     |
| ---------------------- | ---------------------------------------------------- | --------------------------- |
| Cheque ID              | Internal system identifier                           | `CHK-2026-000001`           |
| Cheque Number          | Unique cheque identifier                             | `000123`                    |
| Account Number         | Account associated with cheque                       | `1002345678`                |
| Routing/Transit Number | Banking routing identifier                           | `123456789`                 |
| Payee Name             | Person or organization receiving payment             | `John Doe`                  |
| Amount                 | Numeric cheque amount                                | `25000.00`                  |
| Amount in Words        | Written amount                                       | `Twenty Five Thousand Only` |
| Date                   | Cheque issue date                                    | `15/08/2026`                |
| Bank Name              | Issuing bank                                         | `Demo Bank`                 |
| MICR/Encoded Line      | Machine-readable cheque information where applicable | Bank-specific               |
| Signature Region       | Location/reference to signature area                 | `Detected`                  |

**Important:** The exact fields and formats can vary by country and cheque design. Our implementation should therefore use a configurable cheque template rather than assuming that every cheque has exactly the same layout.

---

# 4. Input

The module receives the OCR result generated by `14_OCR_Engine.md`.

Example:

```json
{
  "cheque_id": "CHK-2026-000001",
  "raw_text": "DEMO BANK\nDate: 15/08/2026\nPay to: John Doe\nAmount: 25,000.00\nAccount No: 1002345678\nCheque No: 000123",
  "average_confidence": 94.2
}
```

Where available, the OCR engine should also provide:

```text
Text
X coordinate
Y coordinate
Width
Height
Confidence
```

These coordinates are useful for identifying the location of fields on the cheque.

---

# 5. Output

The module converts the raw OCR result into structured JSON.

Example:

```json
{
  "cheque_id": "CHK-2026-000001",
  "cheque_number": "000123",
  "account_number": "1002345678",
  "routing_transit_number": "123456789",
  "payee_name": "John Doe",
  "amount": 25000.00,
  "amount_in_words": "Twenty Five Thousand Only",
  "date": "2026-08-15",
  "bank_name": "Demo Bank",
  "extraction_status": "COMPLETED"
}
```

This structured record becomes an input to the **Validation Engine**.

# 6. Extraction Pipeline

The complete process is:

```text
Raw OCR Output
      ↓
Text Cleaning
      ↓
Text Segmentation
      ↓
Field Identification
      ↓
Field Extraction
      ↓
Character Normalization
      ↓
Data-Type Validation
      ↓
Confidence Evaluation
      ↓
Missing/Ambiguous Field Detection
      ↓
Structured Cheque Record
```

# 7. Text Cleaning

OCR output may contain:

* Extra spaces
* Unnecessary line breaks
* Duplicate spaces
* OCR artifacts
* Unexpected special characters

Example:

```text
Raw OCR:

"Pay   to:   John   Doe"
```

After basic normalization:

```text
"Pay to: John Doe"
```

However, cleaning must be conservative.

The system should **not modify the original OCR output**.

Instead:

```text
Raw OCR
   │
   ├──────► Original OCR Storage
   │
   ▼
Normalized OCR
   │
   ▼
Field Extraction
```

---

# 8. Text Segmentation

The normalized OCR output is divided into lines or text blocks.

Example:

```text
DEMO BANK
Date: 15/08/2026
Pay to: John Doe
Amount: 25,000.00
Account No: 1002345678
Cheque No: 000123
```

becomes:

```text
Line 1 → DEMO BANK
Line 2 → Date: 15/08/2026
Line 3 → Pay to: John Doe
Line 4 → Amount: 25,000.00
Line 5 → Account No: 1002345678
Line 6 → Cheque No: 000123
```

These lines can then be analyzed individually.

---

# 9. Field Identification

The system identifies fields using a combination of:

1. Keywords
2. Position
3. Expected data format
4. OCR bounding boxes
5. Cheque template
6. Regular expressions
7. Cross-field validation

For example:

```text
"Date: 15/08/2026"
```

contains the keyword:

```text
Date
```

and the following value matches a date pattern.

Therefore:

```text
Field = Date
Value = 15/08/2026
```

---

# 10. Keyword-Based Extraction

Common keywords can be configured for each field.

Example:

| Field         | Possible Keywords                       |
| ------------- | --------------------------------------- |
| Date          | `Date`, `Dated`                         |
| Payee         | `Pay`, `Pay to`, `Payee`                |
| Amount        | `Amount`, `Rs`, `$` depending on format |
| Account       | `Account`, `A/C`, `A/C No`              |
| Cheque Number | `Cheque No`, `Check No`, `Chq No`       |
| Bank          | Bank-specific/header information        |

These keywords should be configurable rather than hard-coded throughout the application.

---

# 11. Regular Expression-Based Extraction

Regular expressions can be used to identify fields with predictable formats.

### Example: Date

A simplified date pattern may identify:

```text
15/08/2026
```

### Example: Amount

A monetary pattern may identify:

```text
25,000.00
```

### Example: Cheque Number

A numeric pattern may identify:

```text
000123
```

However, regular expressions should be combined with positional and contextual information.

For example, not every six-digit number on a cheque is necessarily the cheque number.

---

# 12. Cheque Number Extraction

The cheque number is an important identifier.

Example:

```text
Cheque No: 000123
```

The extraction process:

```text
Keyword Detection
       ↓
"Cheque No"
       ↓
Extract nearby value
       ↓
Validate expected format
       ↓
Cheque Number = 000123
```

Output:

```json
{
  "value": "000123",
  "confidence": 98,
  "status": "VALID"
}
```

Leading zeros must be preserved.

Therefore:

```text
000123
```

must **not** become:

```text
123
```

because the cheque number is an identifier, not a mathematical value.

---

# 13. Account Number Extraction

The system extracts the account number from the relevant cheque region.

Example:

```text
Account No: 1002345678
```

Output:

```json
{
  "value": "1002345678",
  "confidence": 97,
  "status": "VALID"
}
```

The exact length and character rules should be configurable according to the banking dataset being used.

---

# 14. Routing/Transit Number Extraction

The routing/transit number identifies banking institutions or processing routes depending on the applicable banking standard.

Example:

```text
Routing/Transit: 123456789
```

The system should:

1. Detect the relevant region.
2. Extract the candidate value.
3. Normalize the value.
4. Validate its expected format.
5. Compare it with mock banking records where applicable.

The system should not assume that one routing format applies universally.

---

# 15. Payee Extraction

The payee is generally a text field.

Example:

```text
Pay to: John Doe
```

The extraction process is:

```text
Detect "Pay to"
       ↓
Identify following text
       ↓
Remove unnecessary spaces
       ↓
Normalize text
       ↓
Payee = John Doe
```

Output:

```json
{
  "value": "John Doe",
  "confidence": 96,
  "status": "VALID"
}
```

---

# 16. Amount Extraction

The cheque may contain a numeric amount.

Example:

```text
25,000.00
```

The system converts it into a normalized numeric representation:

```text
25000.00
```

Example:

```json
{
  "value": 25000.00,
  "currency": "PROJECT_CONFIGURED_CURRENCY",
  "confidence": 94,
  "status": "VALID"
}
```

The currency should be configured according to the cheque dataset rather than assumed globally.

---

# 17. Amount in Words

Where the cheque contains the amount in words, the system should extract it separately.

Example:

```text
Twenty Five Thousand Only
```

The system can retain both:

```json
{
  "amount_numeric": 25000.00,
  "amount_in_words": "Twenty Five Thousand Only"
}
```

These two values can later be compared by the Validation Engine.

Example:

```text
Numeric Amount = ₹25,000
Amount in Words = Twenty Five Thousand
                 ↓
              MATCH
```

If they disagree:

```text
Numeric Amount = ₹25,000
Amount in Words = Twenty Thousand
                 ↓
             MISMATCH
                 ↓
          Fraud Indicator
```

---

# 18. Date Extraction

The system extracts the cheque date.

Example:

```text
Date: 15/08/2026
```

It should normalize the date into a standard internal representation:

```text
2026-08-15
```

This makes later comparisons easier.

The Validation Engine can then determine whether the cheque is:

* Valid
* Future-dated
* Too old
* Outside the permitted processing window

---

# 19. Bank Name Extraction

The bank name may be present in the header.

Example:

```text
DEMO BANK
```

The extraction engine can identify it using:

* Known bank names
* Template position
* Text location
* Banking reference data

Example:

```json
{
  "bank_name": "Demo Bank",
  "confidence": 95
}
```

For our prototype, **synthetic bank names and records** should be used.

---

# 20. MICR / Encoded Information

Where applicable, the cheque may contain a machine-readable line near the bottom.

Example:

```text
┌─────────────────────────────────────────────┐
│                                             │
│                 Cheque                      │
│                                             │
│ __________________________________________  │
│                                             │
│  MICR / Encoded Information                 │
└─────────────────────────────────────────────┘
```

The project can initially treat this information as a specialized numeric/text region.

Advanced MICR recognition can be added later if required.

The MVP should clearly distinguish ordinary OCR from specialized MICR recognition.

---

# 21. Signature Area

The signature itself is not treated as ordinary OCR text.

The Data Extraction Module should instead maintain a reference to the detected signature region.

Example:

```json
{
  "signature_region": {
    "detected": true,
    "x": 1200,
    "y": 600,
    "width": 400,
    "height": 150
  }
}
```

The actual signature comparison belongs to:

```text
docs/18_Signature_Analysis.md
```

---

# 22. Positional Extraction

OCR bounding boxes can improve extraction accuracy.

Example:

```text
"Date:"
x = 1400
y = 100

"15/08/2026"
x = 1500
y = 100
```

Because both text elements occur in the same region, the system can associate them.

Conceptually:

```text
Keyword
   +
Nearby OCR Text
   +
Expected Format
   ↓
Field
```

This is more reliable than searching the complete OCR text without considering location.

# 24. Field Confidence

Every extracted field should ideally have an associated confidence value.

Example:

```json
{
  "cheque_number": {
    "value": "000123",
    "confidence": 98
  },
  "account_number": {
    "value": "1002345678",
    "confidence": 97
  },
  "payee_name": {
    "value": "John Doe",
    "confidence": 96
  },
  "amount": {
    "value": 25000.00,
    "confidence": 91
  },
  "date": {
    "value": "2026-08-15",
    "confidence": 94
  }
}
```

Low-confidence fields should be flagged rather than silently treated as correct.

---

# 25. Field Validation

Before sending extracted data to the Validation Engine, basic structural checks should be performed.

Example:

```text
Cheque Number
       ↓
Expected numeric format?
       ↓
YES → Continue
NO  → Extraction Warning
```

Similarly:

```text
Amount
 ↓
Can it be converted to a valid amount?
 ↓
YES → Continue
NO  → Review
```

This is **data-format validation**, not banking validation.

Banking validation belongs to the next module.

---

# 26. Missing Field Detection

Required fields should be checked.

Example:

```text
Required:
✓ Cheque Number
✓ Account Number
✓ Payee
✓ Amount
✓ Date
```

If:

```text
Account Number = Missing
```

the system should produce:

```json
{
  "extraction_status": "PARTIAL",
  "missing_fields": [
    "account_number"
  ]
}
```

This can trigger:

```text
Manual Review
```

rather than allowing an incomplete cheque to proceed automatically.

---

# 27. Ambiguous Field Detection

Sometimes OCR may produce two possible values.

Example:

```text
OCR Candidate 1 → 1002345678
Confidence → 96

OCR Candidate 2 → 100234567B
Confidence → 61
```

The system should select the strongest candidate only when supported by field rules.

Otherwise:

```text
AMBIGUOUS
     ↓
Manual Review
```

This is safer for a financial processing system.

---

# 28. OCR Error Normalization

Common OCR confusions may include:

```text
O ↔ 0
I ↔ 1
S ↔ 5
B ↔ 8
```

However, normalization should depend on the field.

For example:

```text
Account Number:
O → 0 may be considered

Payee:
O → 0 should NOT automatically be performed
```

Therefore, normalization rules should be field-specific.

# 30. Detailed Field Representation

For greater traceability, the system can maintain field-level metadata:

```json
{
  "cheque_number": {
    "value": "000123",
    "raw_value": "000123",
    "confidence": 98,
    "source": "ocr",
    "validation_status": "VALID"
  }
}
```

This allows the system to answer:

* What value was extracted?
* What did OCR originally return?
* How confident was OCR?
* Was the value normalized?
* Did the field pass format validation?

---

# 31. Extraction Status

The module should use clear statuses.

```text
PENDING
PROCESSING
COMPLETED
PARTIAL
AMBIGUOUS
FAILED
```

Example:

```text
COMPLETED
```

means all required fields were extracted successfully.

```text
PARTIAL
```

means some fields were missing.

```text
AMBIGUOUS
```

means one or more fields require human confirmation.

---

# 32. Error Handling

Possible extraction errors include:

| Error                    | System Response           |
| ------------------------ | ------------------------- |
| OCR result empty         | Retry OCR / Manual Review |
| Required field missing   | Mark PARTIAL              |
| Multiple candidates      | Mark AMBIGUOUS            |
| Invalid date             | Extraction warning        |
| Invalid amount           | Extraction warning        |
| Invalid account format   | Extraction warning        |
| OCR confidence too low   | Manual Review             |
| Unexpected cheque layout | Template/manual review    |

The module should never silently replace an uncertain value with a guessed value.

# 33. Sample Extraction Workflow

Suppose OCR produces:

```text
DEMO BANK

Date: 15/08/2026

Pay to: John Doe

25,000.00

Account No: 1002345678

```

The extraction process becomes:

```text

         John Doe

Step 3 → Identify Amount
         25,000.00

Step 4 → Identify Account Number
         1002345678

Step 5 → Identify Cheque Number
         000123

Step 6 → Normalize values

Step 7 → Validate formats

Step 8 → Generate structured record
```

Final output:

```json
{
  "cheque_id": "CHK-2026-000001",
  "cheque_number": "000123",
  "account_number": "1002345678",
  "payee_name": "John Doe",
  "amount": 25000.00,
  "date": "2026-08-15",
  "extraction_status": "COMPLETED"
}
```

# 34. Relationship With Validation Engine

The Data Extraction Module does **not** decide whether the cheque is genuine.

It only prepares the information required for validation.

```text
Data Extraction
       ↓
Structured Cheque Data
       ↓
Validation Engine
       ↓
Banking Record Comparison
       ↓
Validation Results
```

For example:

```text
Extracted Account Number
        ↓
Search mock banking database
        ↓
Account exists?
        ↓
YES / NO
```

# 36. Security and Privacy

Because cheque data may contain sensitive financial information:

* Real customer data must not be committed to GitHub.
* The repository should use synthetic/sample cheque data.
* Account numbers should be masked in application logs.
* Raw OCR results should have controlled access.
* Database credentials must not be stored in source code.
* API keys must be stored using environment variables/secrets.
* Audit records should avoid unnecessary exposure of sensitive values.

Example log:

```text
Account: ******5678
```

instead of:

```text
Account: 1002345678
```

The module shall:

1. Receive OCR output.
2. Normalize OCR text.
3. Segment OCR output into logical text blocks.
4. Identify cheque fields.
5. Extract cheque number.
6. Extract account number.
7. Extract routing/transit information where applicable.
8. Extract payee name.
9. Extract numeric amount.
10. Extract amount in words where available.
11. Extract cheque date.
12. Identify bank name where applicable.
13. Record signature-region information where available.
14. Validate basic field formats.
15. Record field-level confidence.
16. Detect missing fields.

18. Produce structured cheque data.
19. Pass structured data to the Validation Engine.

## 43. Summary

The **Cheque Data Extraction Module** acts as the bridge between OCR and banking/fraud validation. It converts unstructured OCR output into a reliable, structured representation of the cheque while retaining confidence, source information, and extraction status.

The design prioritizes **accuracy, traceability, security, and safe handling of uncertainty**. In particular, the system should never treat a low-confidence OCR result as unquestionably correct. Uncertain or incomplete extraction should be routed toward additional processing or manual review.

This structured record will be the primary input for **`16_Validation_Engine.md`**, where we will define the actual banking-record checks such as **cheque-series validation, account-status validation, date-window validation, payee matching, and duplicate checking**.
